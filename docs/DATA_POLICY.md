# Eidolon Data Policy (v2)

## Purpose

This document defines the data-governance rules for Eidolon v2, an
adversary-mirrored OSINT + password-risk research system. The project is
defensive and research-oriented; its data handling makes that obvious in
practice, not just in intent.

Eidolon v2 operates on **consented subjects only** and persists **derived,
typed observations only**. The retired v1 synthetic/preset pipeline
(`generate-profiles`, preset-driven experiments, threshold sweeps) is no longer
part of the data flow and its data classes no longer apply.

## Core rules

1. **Derived Observations only — no raw scrape persisted.** Collectors emit
   typed `Observation` records (`src/eidolon/core/evidence.py`): one
   provenance-stamped, confidence-scored fact each (`subject_id`, `source`,
   `attr_kind`, `value`, `confidence`, `collected_at`, `provenance`, `mirrors`).
   Raw HTML/text is dropped after extraction. No flattened profiles, no raw
   dumps.
2. **Owned / consented allowlist.** Collection runs only against subjects backed
   by a signed `ConsentRecord` in the active roster, enforced by the
   `require_consent` hard gate (`src/eidolon/core/identity.py`). A
   per-subject `allowed_sources` allowlist further restricts which collectors may
   run. Non-roster subjects are refused with `ConsentError`.
3. **`configs/consent_records/` is gitignored and never committed.** Signed
   consent artifacts referenced by each roster entry's `consent_ref` stay local.
   Only the clearly-fake example roster (`configs/osint_roster.example.json`) and
   the clearly-fake snapshot fixtures (`configs/snapshots/*.json`) are tracked.
4. **No raw PII in the repo.** No real personal data, no real passwords, no raw
   scraped pages are ever committed. The transient collection cache lives under
   `artifacts/osint_cache/`, which is gitignored.
5. **Dummy-account data is fake by construction.** Operator-created dummy
   accounts are seeded with fabricated trivia and used only as OSINT *sources*
   (see `docs/OSINT_COLLECTION_PROTOCOL.md`). Their committed fixtures contain no
   real individual's data.

## Allowed data classes

- consented subject observations (derived, typed, minimized),
- operator-created dummy-account observations (fabricated trivia, used as
  sources),
- operator-authored consented snapshots for gated/manual sources,
- local configuration files,
- public or academic password corpora used **only** for aggregate structural
  pattern analysis (e.g. breach structure priors), never for identity linkage,
- saved experiment artifacts generated by the repository itself under
  `artifacts/` (gitignored).

## Disallowed or restricted data classes

Eidolon v2 must not collect or persist:

- real user passwords or raw credentials from live systems,
- raw scraped profile pages or HTML,
- unauthorized personal dossiers on non-consented individuals,
- scraped data gathered in violation of platform terms (ToS-hostile sources
  enter only via operator-authored consented snapshots),
- breach **cleartext** for third parties (only breach names + structure priors),
- newly compiled exploit-oriented password dictionaries for real people,
- concrete guess strings emitted by the predict layer.

## Working rule

If a dataset meaningfully increases the risk of profiling or targeting a real
individual, it is out of scope for the default repository workflow. Consented
subjects and fabricated dummy accounts are the only in-scope data.

## Source handling expectations

### Consented sources

All collection requires a signed consent record. Source access modes are fixed
per `SourceClass` (see `docs/OSINT_COLLECTION_PROTOCOL.md`): live API for owned
`CODE`/owned `SOCIAL`; owned-allowlist HTTP for enumeration/footprint/web; and
**manual snapshot only** for `PROFESSIONAL`, `PUBLIC_RECORDS`, and breach
cleartext. ToS-hostile and invasive sources are never auto-scraped.

### Academic / breach password corpora

When password corpora are used for modeling:

- use them only for aggregate **structural** feature learning (structure priors),
- avoid any identity linkage,
- never map a real person to a corpus-derived guess set,
- store only the derived structure prior (e.g. `word+4digits`), never cleartext.

## Storage and retention

- Persist only derived `Observation`s; delete raw source text after extraction.
- `artifacts/` and `artifacts/osint_cache/` are gitignored.
- `configs/consent_records/` is gitignored (only `.gitkeep` tracked).
- Separate identifiers from derived scoring datasets where practical.
- Version evaluation outputs, not sensitive source inputs.
- On consent withdrawal, delete the consent record and all derived observations
  for that subject.

## Logging

Logs should prefer analyst action metadata, policy/model version identifiers,
artifact paths, and timestamped execution summaries. Logs must avoid storing
candidate passwords, raw scraped text, guess strings, or unnecessary personal
profile payloads.

## Access control

- keep experiment directories and consent records local,
- avoid syncing private datasets or consent records into public remotes,
- for future organizational deployments: restrict analyst access by role,
  require audit logging for bulk scoring, and separate evaluation environments
  from production identity systems (see `docs/ENTERPRISE_ARCHITECTURE.md`).

## Publication guidance

Research outputs should report only aggregate statistics, describe consented or
fabricated dummy-account sources clearly, avoid examples that reconstruct a real
user's secrets, and explain how exposure scoring differs from offensive password
guessing.
