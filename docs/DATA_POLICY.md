# SignalLock Data Policy

## Purpose

This document defines the current data-governance expectations for SignalLock.

The project is defensive and research-oriented. Its data handling should make that obvious in practice, not just in intent.

## Allowed Data Classes

SignalLock is currently designed for:

- synthetic public profiles,
- organization-approved mock rosters,
- local configuration files,
- public or academic password corpora used only for aggregate pattern analysis,
- saved experiment artifacts generated by the repository itself.

## Disallowed or Restricted Data Classes

The current prototype should not be used to collect or persist:

- real user passwords,
- raw credentials from live systems,
- unauthorized personal dossiers,
- scraped profile data gathered in violation of platform terms,
- newly compiled exploit-oriented password dictionaries for real people.

## Current Working Rule

If a dataset meaningfully increases the risk of profiling or targeting a real individual, it is out of scope for the default repository workflow.

## Source Handling Expectations

### Synthetic First

Default development and testing should use:

- `generate-profiles`,
- preset-driven synthetic experiments,
- locally generated artifacts under `artifacts/`.

### Organization-Approved Contexts

If this project is adapted for a real authorized environment, inputs should come from:

- an approved employee roster,
- organization-controlled profile snapshots,
- explicit research or security-operations approval.

### Academic Password Corpora

When password datasets are used for later model training or calibration:

- use them only for aggregate feature learning,
- avoid any identity linkage,
- do not add tooling that maps a real person to a corpus-derived guess set.

## Storage and Retention

Current repository expectations:

- generated experiment artifacts are local,
- `artifacts/` is gitignored,
- internal planning files remain outside the public repository when appropriate,
- raw source data should not be copied into the repo unless it is synthetic or clearly redistributable.

Recommended retention practice for future real-world studies:

- retain only derived features needed for analysis,
- delete raw profile text when no longer required,
- separate identifiers from derived scoring datasets,
- version evaluation outputs, not sensitive source inputs.

## Logging

If a future dashboard or audit mode is implemented, logs should prefer:

- analyst action metadata,
- policy version identifiers,
- model version identifiers,
- artifact paths,
- timestamped execution summaries.

Logs should avoid storing:

- candidate passwords,
- raw scraped text,
- unnecessary personal profile payloads.

## Access Control

For the current CLI-first prototype:

- keep experiment directories local,
- treat saved bundles as research artifacts,
- avoid syncing private datasets into public remotes.

For future organizational deployments:

- restrict analyst access by role,
- require audit logging for bulk user scoring,
- separate evaluation environments from production identity systems.

## Publication Guidance

Research outputs from SignalLock should:

- report only aggregate statistics,
- describe synthetic or consented data sources clearly,
- avoid examples that reconstruct real-user secrets,
- explain how exposure scoring differs from offensive password guessing.

## Open Follow-Up

As the repository evolves, the next governance additions should likely include:

- a source allowlist template,
- a retention checklist,
- an ethics review checklist for studies involving non-synthetic data,
- a model-card style note for any future trained predictor.
